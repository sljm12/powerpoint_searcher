# EX1 Linux capacity run, 2026-11-05

The locked service ran on Ubuntu 24.04 under WSL2, Python 3.12.3, with 20 reported CPUs. The initial load average was 0.15, 0.20, 0.24. Service data lived in a fresh private Linux filesystem directory. The output summary records the exact service-source snapshot, capacity-probe hash, fixture hash, conditions, every deck result, and measured counts. The runner kept the service on loopback and stopped it after the probe.

The run completed 105 deck jobs with zero failed jobs. The first five were serial repetitions of the same 20-slide fixture. Their upload, poll, manifest, and full asset-download wall time had a median of 4.381 seconds and a range of 4.220 to 4.792 seconds. The remaining 100 unique deck identities completed sequentially. Every job checked all 20 slides, all named source shapes, table and chart kind/text, nested group parentage, 20 distinct picture occurrences sharing one original byte asset, and the checksum and dimensions of every downloaded asset.

All 100 retained decks were then deleted through the API. The logical private data directory measured 48,763,213 bytes before deletion and 11,763,713 bytes after deletion and after the two-second growth check. The remaining size is service metadata and deletion tombstones, not slide assets. The report counted 8,245 HTTP requests. Sampled peak service-descendant RSS was 410,341,376 bytes; sampled renderer-scope cgroup memory was 175,226,880 bytes; the maximum sampled combined value was 535,650,304 bytes.

This single WSL2 run confirms that this fixture set completed at this load. It is not a target-hardware benchmark or a comparison with trunk or LibreOffice-only extraction. The OS page cache was not flushed, the renderer starts a new private office profile per job, and memory values are sampled at 0.5-second intervals. No 20-slide profile was collected, so the timing limiter is uncharacterized. These values do not establish cold-cache latency, a production SLO, or broader library capacity.
